# 实现思路（DESIGN）

> 回答四个问题：问题怎么建模的？为什么这么分层？解码器为什么是核心？动态重排怎么保证"计划不翻烧饼"？

## 1. 问题建模

### 1.1 实体关系

```
Order 订单 (code, product, qty, release, due, priority, urgent)
  └─> Routing 工艺路线 (product → 有序工序列表)
        └─> OpInst 工序实例 (seq, family 换型族, qty, options[])
              └─> MachineOption (machineIdx, unitSeconds 单件工时, double)
Machine 设备 (code, group, calendar 日历, down 停机标记)
SetupMatrix 换型矩阵 (族A, 族B) → 准备秒数
Calendar 日历 (workdays + shifts) → Timeline 可用时段段表
```

一张订单按其工艺路线展开成 `n` 道工序实例，存进 `Problem::ops`（扁平数组，下标即 op id），
`Problem::orderOps[order]` 保存该订单的工序链。排产的输出是
`Solution::assign[op] = {machine, start, end, setup, occStart, workSec, frozen}`。

### 1.2 时间模型（三个容易被忽略的坑，都踩过）

时间是 `int64` Unix 秒。加工跨班次时，有三个不同的"时长/起点"：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `start/end` | 时钟上看到的开始/结束 | 甘特图横轴 |
| `occStart` | 机器**真实被占用**的起点（换型可能被午休切开） | 日历校验：`start - setup` 只是时钟回退，不是占用起点 |
| `workSec` | 纯加工产能秒数（qty × unitSeconds） | KPI 利用率：`end-start` 含跨班次空闲，会虚高 |

推时间一律走 `Timeline` 的三个原语：`alignStart`（对齐到可用时段）、`advance`（按可用产能前进）、
`rewind`（按可用产能回退）。**绝不做 `end - dur` 这种时钟减法**——跨班次必错。

### 1.3 约束与目标

硬约束（违反即不可行，由校验器把关）：
1. 同设备同时刻互斥；
2. 同订单按工艺链先后；
3. 加工+换型必须落在设备日历可用时段内；
4. 工时一致性（`workSec == qty × unitSeconds`）。

目标函数（加权求和，权重在 `Problem::weights` 可配）：

```
minimize  w_t · Σ(延期小时 × 优先级权重, 急单 ×1.5)
        + w_s · Σ(换型分钟)
        + w_m · makespan(小时)
```

## 2. 三层求解架构

```
           ┌─ IScheduler::solve(Problem, SolveOptions) → Solution ─┐
           │                                                        │
 L1 规则法  │  RuleScheduler   六条规则全跑, 取目标值最优          秒级兜底/给 GA 当种子
 L2 遗传算法│  GaScheduler     OS+MS 编码, 多岛并行, 关键工序局部搜索  预算可控的主力求解器
 L3 CP-SAT │  (接口预留, 未实现)                                     最优性基准尺
           └────────────────────────────────────────────────────────┘
                    所有求解器共用 → Decoder(插入式解码) + Validator(V1~V6)
```

**关键设计：解码器独立于求解器。** 规则法决定"按什么顺序派工"，GA 决定"顺序+设备"的编码，
但"一道工序放到哪台设备哪个时刻"只有一个实现（`Decoder`）。好处：

1. 规则解和 GA 解在**同一个评价标准**下比较，不会出现"各说各话"；
2. GA 可以直接把规则解**原样继承为种子个体**（见 ALGORITHMS.md §3），起点即规则最优；
3. 换型/跨班次/插入逻辑只写一遍，只调一处 bug。

## 3. 解码器：插入式放置 + 顺序自愈

`decodeSequence(opOrder, ms, chooseBestMachine)`：按派工顺序逐道工序，

1. 算最早可开工时刻 `ready = max(订单release, 前道结束)`；
2. 在候选设备的机器队列里**从前往后找第一个可行空隙**（插入式，不是追加到队尾——
   能把活塞进已有工序前面的空档，解质量高一档）；
3. 空隙合法性 = 后道工序接得上（换型出向时间够 + 不重叠），跨班次时用 `capacity()` 判可用产能；
4. 设备选择：`chooseBestMachine=true` 时遍历所有可选设备取最早完工；GA 模式则按 `ms` 编码定位。

**性能关键**：候选位置扫描前先做整数剪枝——日历可用产能 ≤ 时钟跨度，若"到后道开工的时钟差
都不够 setup+dur"必插不进，直接跳过，省掉绝大多数 `Timeline` 查询（2400 工序下解码 ~3.5 倍加速）。

**顺序自愈（保证 100% 可行输出）**：插入式解码在"换型+跨班次+多机联动"叠加时，极端情况下会留下
重叠或"后道早于前道"。与其追逐每个边界情况，不如统一兜底：

1. 同机器：按时间轴重扫，重叠就整体顺延（只推后不提前）；
2. 跨机器：按派工顺序单趟扫描工艺链，前道被推后就把后道连锁顺延（`relayoutFrom`），
   最多 4 趟收敛。

代价是极少数工序晚几分钟，换来的是"任何求解器出来的解结构完整且可行"，前端和校验器都不会见到非法解。

## 4. 动态重排：冻结 + 局部修复 + 稳定性代价

所有重排共用一套纪律：**已开工工序冻结（`frozen=true`），只动未开工部分，绝不全表重排。**

| 事件 | 处理 | 输出 |
|---|---|---|
| 急单插队 | 新订单工序按最早空隙插入未冻结时段；必要时局部顺延 | 漂移工序数、稳定性代价 |
| 设备故障 | 该设备日历从 `now` 起整段清空（**不改工艺路线**——已开工工序仍合法），未开工工序迁移到同组设备 + 连锁顺延 | 迁移数、漂移数、稳定性代价 |
| 设备恢复 | 日历恢复，提示重新排产 | — |
| 滚动时域 | 窗口外不排，窗口滑动时重复利用上述修复 | — |

稳定性代价 = `Σ|开工时间偏移| + 换设备次数 × 惩罚`，与优化目标并列展示——
重排方案好不好，除了"目标值"，还要看"车间要不要为此翻一遍工卡"。

实现上还踩过一个坑：故障迁移后直接**重放原解的派工顺序**（`Solution::opOrder`，
解码器落盘的实际放置顺序），只对受影响的机器段做 `relayoutFrom`，不做全量重新解码——
这是"计划漂移"可控的根本原因。

## 5. 校验器（信任边界）

每个求解器输出的 `Solution` 都过一遍独立实现的 `validate()`，不共享解码器代码：

- V1 每道工序都有安排、工时与 `qty × unitSeconds` 一致；
- V2 设备支持该工序；
- V3 加工+换型全部落在设备日历可用时段；
- V4 同设备无重叠；
- V5 工艺链先后；
- V6 冻结工序未被移动。

API 层把校验结论（`PASS` / 违规摘要）随结果一起返回——**"可信"由校验器保证，不由求解器自称**。
